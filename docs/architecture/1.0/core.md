# Architecture — core

A living record of decisions made so far. This is not a spec — it's a snapshot to stop us re-deciding the same thing twice.

Cross-cutting model that every component below relies on. Per-component detail (what each tier's services actually do) lives in its own file — see the [docs index](../../../README.md#documentation) or jump straight to [applications](applications.md), [domain services](domain-services.md), [business services](business-services.md), [platform services](platform-services.md), [infrastructure](infrastructure.md).

## Philosophy

Microverse is a polyglot playground: every component gets to have its own technology, its own personality, and its own reason for existing. Consistency isn't the goal — clarity of *role* is.

## The four tiers

```
Applications        — the front doors (TaskFusion, Admin, LAReports)
Domain services      — one specialist trick each, customer-facing brand names
Business services    — the narrator, owns the plot
Platform services     — plumbing, zero business opinions, fully generic
Infrastructure        — the ground everything stands on
```

**The test for each tier**, in case a new service shows up later and you're not sure where it goes:
- **Platform service** — could this get dropped into a totally unrelated app unchanged? If yes, it's plumbing.
- **Domain service** — does it do exactly one specialist trick, with a real opinion about *what* it's analyzing/processing? If yes, it's a specialist.
- **Business service** — does it know what an Order or a Quest *is*? If yes, it's the narrator.

See [domain-services.md](domain-services.md), [business-services.md](business-services.md), and [platform-services.md](platform-services.md) for the current service tables per tier.

## Kafka vs RabbitMQ

- **Kafka = the scroll.** Immutable, replayable. Anything that needs a permanent record: `time_entry.completed`, `sentiment.analyzed`, `kudos.given`, tier changes.
- **RabbitMQ = the pigeon.** Fire-and-forget delivery: "send this email," "process this image," "nudge this analyst." Disposable — if nobody's home, it just doesn't land.
- Most interesting events do both: Kafka remembers it happened, RabbitMQ tells someone right now.

## Entity model

- **Account** — a company or an individual (`type: 'company' | 'individual'`). Every Customer belongs to exactly one Account, always — an individual gets an Account of their own rather than being forced into a fake one-person "company." Billing (rustledger/billing-service) bills the Account, not individual customer logins.
- **Project** — sits between Account and Order/Task. An Account has many Projects (an ongoing engagement, e.g. "Acme's Q3 Sentiment Monitoring"), and a Project *is* the contract unit (see [docs/business/1.0/overview.md](../../business/1.0/overview.md)) — not a separate `contracts` table. Has one responsible/main user (any role — PM, senior analyst, etc., not locked to PM) and groups many Orders/Tasks under it.
- **Customer** — a login under an Account. 1:n — an Account (company-type) can have multiple customer users, an individual-type Account has one. Creates Orders, has Invoices via its Account.
- **Order** — what a customer submits (media + service type). Carries a `service` tag (e.g. `gofeeler`) tying it to the domain service it came through. Comments are the one exception to "extra detail lives as attributes, not separate records" — they're versioned (every edit is a new row) and threaded (one level of replies, internal-vs-customer-facing via a `visibility` column), which doesn't fit a JSON attribute; see [docs/schema.md](../../schema.md)'s `task_comments`.
- **Task** — an Order once a PM assigns it to an Analyst. Stays 1:1 with its Order.
- **Analyst** — human or agentic. Has a rating, performance history, message history to their PM.
- **Project Manager** — human or agentic. Assigned to a specific account, handles that account's Orders. Claims Tasks from the pool, assigns to Analysts, gives kudos.
- **Invoice** — generated by rustledger from elixtempo's tracked time.
- **Kudos** — given by PM or Customer to an Analyst; feeds Djaboard's leaderboard.

**ID convention:** all entity IDs are UUIDs, not incremental integers — prevents enumeration (guessing adjacent order/task IDs), lets services generate IDs independently without coordination, and keeps object storage paths from leaking business volume. Use time-ordered UUIDs (UUIDv7, or `gen_random_uuid()` via pgcrypto where v7 isn't available) rather than random UUIDv4, to avoid B-tree index fragmentation on insert-heavy tables like the task pool.

## Roles and permissions

Two-dimensional model, requiring both to grant access:

- **Platform function** — `platform:customer`, `platform:project-manager`, `platform:analyst`, `platform:reviewer`, `platform:admin`
- **Service scope** — `service:gofeeler`, `service:springpix`, `service:pyreel`, etc.

A person needs both claims for a given action — e.g. GoFeeler's Create Order page requires `platform:customer` + `service:gofeeler`. This replaces the earlier single combined-string model (`gofeeler:project-manager`) — someone who works across multiple services now holds one platform function role plus each relevant service scope, instead of a separate combined role per service.

**Exception: `platform:admin` has nothing to do with services.** Every other platform function only makes sense paired with a service scope — a project-manager or analyst is always *for* something (`service:gofeeler`), because they participate in that service's actual task workflow. Admin doesn't — managing users or platform-level settings isn't domain work that happens *per-service*, so there's no such thing as "admin, but only for GoFeeler." `platform:admin` grants access on its own, full stop; there's no `service:*` pairing to check, and none would mean anything if there were.

**Page-level access vs. data-level filtering — the Project Hub.** Getting *into* the Project Hub page requires `platform:project-manager` plus *any* `service:*` claim — it doesn't matter which, since the page itself spans whatever services a PM manages. Admin needs no service scope because it isn't service-specific at all; the Project Hub needs *some* service scope because it very much is, just not committed to one in advance.

**Two independent checks govern what a PM actually sees, not one combined thing.** Ownership and service-capability are separate axes:
- **Ownership** (`pm_accounts`) — which Accounts this PM can see at all.
- **Service scope** (`service:gofeeler`, etc.) — which task *types* they can act on, once inside an Account they own.

A PM needs **both** for any given task: they must own the Account (via `pm_accounts`) *and* hold the service scope matching that task's service. This is exactly why `pm_accounts` was designed many-to-many from the start — multiple PMs can share one Account, each scoped to different services. E.g. Matthew could own Acme Forestry's GoFeeler work while Lydia owns its SpringPix work — same Account, different service lenses, so other PMs can work the same Account without seeing every service on it.

**An Account can span multiple services, intentionally.** `tasks.service` is per-task, not per-account — nothing forces one Account into one service, and it shouldn't: a client buying a second service (GoFeeler → GoFeeler + SpringPix) is literally the "Upsell" glossary term in action (see [docs/business/1.0/overview.md](../../business/1.0/overview.md)).

**Deactivated users (`users.active = false`)** keep the ability to log in — Keycloak doesn't know or care about this flag, it's task-service's own bookkeeping (see [docs/schema.md](../../schema.md)). What they lose is everything except two things: the My Profile page (4.0.4, accessible to any logged-in user regardless of role or active status) and Keycloak's own account console (email/name editing, password change) — themed to match Microverse via Phase 11's Keycloak theme rather than rebuilt as a separate in-app page, so this stays an external redirect, not a task-service-hosted route. The frontend shows this as a scrim — a translucent overlay over visible-but-non-interactive app content — but **the scrim is a UI affordance only, not the security boundary**. Real enforcement is server-side, and cheap to add: task-service's existing `syncUser` middleware already runs on every request and has the user row in hand right after its upsert — the active check is just an additional branch there (reject with 403 for anything not on the My-Profile/health-check allowlist), not a new mechanism (see [docs/schema.md](../../schema.md)'s `users` section for the implementation note).

- Humans can hold multiple service scopes at once.
- Agents are simply assigned roles the same way — no separate agent-identity model needed.
- Roles map directly to Keycloak realm/client roles — permission checks are just "does the JWT contain both claims," not custom application logic.

**Role vs. assignment — an important distinction.** A role only grants broad *eligibility* ("can this person ever act as an analyst for GoFeeler") — it is never per-project. The actual per-task function comes from `Task.assignee_id`. A person being analyst on one Order and reviewer on another doesn't need a third role dimension — they simply hold both `platform:analyst` and `platform:reviewer` (plus `service:gofeeler`), and which one applies on any given Task is just whatever they're currently assigned as. Conflict-of-interest rules (e.g. blocking someone from reviewing their own prior work, or work for a competing company) are **not** enforced by the role model — that's deferred as a future business decision, to be handled as an assignment-time check in task-service if/when it's actually needed.

## Task workflow

A Task has a Jira-ticket-style status, owned by `workflow` (Camunda):

```
unassigned → analyst → reviewer → done → paid → closed
                ↑___________|
                  (rejected)
```

- **Analyst** and **reviewer** are two distinct roles (`gofeeler:analyst`, `gofeeler:reviewer`) — one human can hold both, but a single Task always has exactly one active assignee at a time.
- **Backward transitions are allowed**: a reviewer can reject work, sending the Task back to `analyst`. Rejection requires an assignee — the transition isn't complete until a new analyst is picked, so a Task never sits unassigned mid-rejection.
- **Assignee vs owner** — these are different fields, deliberately, to avoid the Jira annoyance of a "done" ticket still sitting under someone's name:

  | State | Assignee | Owner |
  |---|---|---|
  | unassigned | — | the customer |
  | analyst | the analyst | the analyst |
  | reviewer | the reviewer | the reviewer |
  | done | — | PM |
  | paid | — | customer |
  | closed | — | — |

- Reaching **paid** unlocks the results for the customer to download.
- The assignee must always match the current state's required role — a transition shouldn't be allowed to complete without a valid assignee holding the right role for the new state.
- **Owner starts as the customer, not blank** — `task-service`'s `create()` (`business-services/task-service/models/task.js`) sets `owner` to the creating customer's email at insert time; `assignAnalyst` overwrites it once a PM assigns someone. Deliberate, not an oversight: before assignment the order is exclusively the customer's to act on (edit/cancel), and customer-facing views keyed on `owner === <their identity>` need that to resolve correctly for their own fresh order, not just once it reaches `paid`. Prefer `customer_id` over `owner` for "is this my task" checks that need to hold across every state, though — `owner` still moves on once assigned, so anything customer-facing that needs to survive past `unassigned` (e.g. their own comment thread, order-progress view) should never key off it.

See [business-services.md](business-services.md) for where the task pool itself lives.

## Recently resolved

- **Agents and search-service** — human-only, not for agents.
- **`messaging` naming collision** — renamed the pub/sub abstraction to `event-bus`; `messaging` is now the human (and possibly agent) communication feature (popup, newsfeed, email — no chat).
- **Order-to-Task cardinality** — confirmed 1:1; extra detail lives as attributes, not separate Tasks.
- **Customer entity** — can be a company or an individual; 1:n, a company can have multiple customer users.
- **PM-to-company assignment** — a PM is assigned to a specific company and works that company's orders.
- **Rejection assignee** — rejection requires picking a new assignee immediately; a Task never sits unassigned mid-rejection.
- **Rejection target** — the reviewer picks from the pool (a Scout-ranked candidate list, same mechanism the PM's initial assignment uses), not automatically the same analyst who did the original work. Reviewer identity itself is the account's PM by default (set when the analyst moves a Task to review), reassignable to a dedicated `platform:reviewer` holder — see [domain-services.md](../../roadmap/1.0/domain-services.md)'s 4.5.
