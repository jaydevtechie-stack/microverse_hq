### Proposals

Approach + technology notes for roadmap items that need more than a one-line bullet.

#### Sentiment tag input (GoFeeler)
**Approach:** Open vocabulary — tags are added on the fly, no separate dictionary-maintenance workflow. Typing a tag that doesn't fuzzy-match an existing one just adds it as a new tag in the shared vocabulary. To curb near-duplicate drift ("Frustration" vs "Frustrated" vs "Frustrating"), the fuzzy match should nudge toward an existing close tag before letting a new one get created.
**Storage:** A shared `tags` index in Elasticsearch, owned by `search-service` — not a per-service table. One document per tag (`{ name, created_at, usage_count }`). Any domain service that needs tag autocomplete queries the same index, rather than each service growing its own bespoke vocabulary.
**Tech:** Elasticsearch's built-in fuzzy matching (`fuzziness: "AUTO"` on a match query) does the typo-tolerant matching server-side — no separate client-side fuzzy library (Fuse.js) needed. Frontend is a combobox pattern (`cmdk` or `downshift`) calling search-service's tag-suggest endpoint. Selected tags render as a chip cluster, not a literal size-by-frequency word cloud. `usage_count` could later power a genuine frequency-based view (e.g. "most common tags this month") as a separate analytics feature.

**Implemented as:** `GET /tags/suggest?q=` on search-service, proxied through nginx at `/api/tags`. Fuzziness alone turned out not to be enough — edit distance between a short in-progress prefix ("urg") and the full word ("urgency") is way past what `fuzziness: AUTO` allows, so early keystrokes returned nothing. Fixed with a `bool`/`should` combining `match_bool_prefix` (catches mid-typing) and the fuzzy `match` (catches typos on an otherwise-complete word, e.g. "urgncy"). `POST /tags` does the upsert-or-bump-usage_count on pick/create, matched case-insensitively via a `name.keyword` field with a lowercase normalizer. `name.keyword` (not analyzed `name`) is deliberate for that lookup — fuzzy/prefix matching is for suggestions, not for deciding whether a submitted tag is "the same" as an existing one. Index gets seeded with the starter sentiment vocabulary (positive/negative/.../escalation) on first creation only.

The stored `name` itself is now lowercased + trimmed at write time (`create_or_bump_tag`), not just matched case-insensitively — the keyword normalizer above only made "Urgency" and "urgency" resolve to the same document, it didn't stop whichever casing got typed *first* from sticking permanently as the display value for every subsequent match. Existing indexed tags were normalized in place via a one-time `_update_by_query` when this was caught (17 docs, no case-collisions to merge).

#### Task search index (GoFeeler)
**Approach:** Faceted per-service indices (`tasks-<service>`) rather than one flat `tasks` index — service-scope becomes index routing, not a query-time filter, matching Branch 6's discovery-scoped resolution (analyst/reviewer see every task in their own service, not just their own assignments). An ES index template (pattern `tasks-*`) defines the mapping once; any matching index — the 7 known services today, or a future one — inherits it automatically on first write, no per-service index needs manual creation.
**Storage:** One document per task, `_id = task_id` so future lifecycle-driven writes (Branch 6.2) are idempotent upserts, not append-only. Analyzed fields are the actual query targets — `title`, `context`. Everything else is keyword-only (filter/narrowing, never relevance-matched): `status`, `tags`, `owner`, `customer_id`, `account_id`, `project_id`, `assignee_ids` (kept for a future "my tasks" narrowing/ranking option even though base access doesn't need it). `created_at`/`assigned_at` are dates. No `service` field — it's implicit in which index a document lives in.
**Tech:** `search-service`'s Python/`elasticsearch` client gets a `put_index_template` call (mirroring the tags index's `ensure_index` pattern) instead of a single named-index create — the template lazily governs any `tasks-*` index ES creates later, so nothing needs to loop over services or pre-create anything. A `service_index_name(service)` helper (`tasks-{service}`) is the one place that computes the name, so Branch 6.2's consumer and 6.4's query endpoint can't drift into disagreeing conventions. No-index handling (Branch 6.3) is a delete against the doc, not a mapping concern — nothing here. Comments indexing is explicitly out of scope for this pass.

#### Audit log & efficiency metrics (GoFeeler)
**Approach:** A new `audit-service` (Node/kafkajs/pg, sibling to `notification-service`) runs a third independent Kafka consumer group on `task-service`'s existing `task-service.tasks` topic — standard fan-out, no change to search-service's or notification-service's own consumers. Every row is written verbatim off whichever event arrives: no diffing against a "previous" row, no extra state lookup — the event name already encodes the transition semantics (`task.assigned` is always `unassigned`→`analyst`, etc.), and each event already carries its own post-transition `status`/`owner`/`assignee_ids` (full snapshot, same as `task-service`'s other consumers rely on). "Time-in-status" and "how fast an analyst reacts to a new assignment" are both derived at query time via `LEAD()` window functions over consecutive rows per `task_id`, not stored — "audit trail is built from this stream, not a separate write path" taken literally.
**Storage:** `audit_log` on the shared `microverse-postgis` instance (see [docs/schema.md](../../schema.md) for the DDL). `task_id` is a plain UUID, cross-service reference to `task-service`'s `tasks.id`, not FK-enforced — same posture as `notifications.task_id`.
**Tech:** `sentiment.analyzed` — GoFeeler's own new event — is published from a Kafka producer added directly to GoFeeler's Go backend (new `events` package, `segmentio/kafka-go`), and deliberately lands on a **separate** topic, `gofeeler.sentiment`, not `task-service.tasks`: `search-service`'s indexing consumer (Branch 6.2) treats every message on that topic as a full task-state upsert with no event-name filtering, and a `sentiment.analyzed` payload shares none of `taskToEvent`'s fields — landing it there would blank real Elasticsearch documents on the next re-index. `audit-service` subscribes to both topics from one consumer group, dispatching on Kafka's `topic` field per message, rather than running two separate consumer groups for what's ultimately one write path. `duration_ms` (GoFeeler's own processing-time efficiency metric) is measured at the source — wrapping the existing `eng.Analyze` call in `handler/setiment.go` — rather than inferred later from two separate events; this is also how the open question below got resolved. Access control: `GET /audit/events` (recent activity), `GET /audit/tasks/:taskId` (timeline), and `GET /audit/metrics/{processing-time,reaction-time}` are gated `platform:admin` OR `platform:project-manager` (see 4.3's resolution below, which already earmarked the eventual audit log as Admin's cross-account visibility tool; PM access added so PMs can pull their own accounts' numbers too). Shipped backend-only first — an explicit documented gap matching this codebase's established backend-ahead-of-frontend pattern (5.2.1/5.2.2/6.3.1) — then closed by `AdminAuditLogPage.js` filling in `nav-config.json`'s already-reserved `/admin/audit-log` tab.

- ✅ **Live-verified end to end** — a real Stripe test-mode Checkout Session was paid ($200, task `4e86966c-ec43-461b-b163-a6647c0c9551`) and the full chain confirmed: webhook → `bills.status = 'paid'` (with real `stripe_payment_intent_id`/`stripe_checkout_session_id`) → `bill.paid` on Kafka → task-service's consumer flips `tasks.status` to `paid`. Getting here required tunneling events in via the Stripe CLI, since `microverse.local` isn't publicly reachable — the official `stripe/stripe-cli` Docker image (no native install needed) running on the compose network, targeting nginx by container name — see [docs/development/TESTING.md](../../development/TESTING.md)'s Branch 9 section. Two real bugs surfaced during verification, both fixed:
  - `parse_checkout_completed` (`stripe_client.rs`) deserialized webhooks into `async-stripe` 0.41.0's typed `Event`/`CheckoutSession`, which is generated against a fixed Stripe API version (`2023-10-16`, see the crate's `resources/generated/version.rs`). A live Stripe account defaults to its *current* API version (`2026-07-29.dahlia` here) with no CLI flag to pin `stripe listen` to an older one, so multi-year schema drift on fields we don't even use broke deserialization of the whole event — `checkout.session.completed` consistently 400'd while other event types (shallower payloads) happened to still parse. Fixed by reimplementing the (simple, version-independent) HMAC signature check ourselves and reading only the 3 fields actually needed (`client_reference_id`, session `id`, `payment_intent`) off untyped `serde_json::Value`, instead of the crate's typed model.
  - `APP_BASE_URL` (Stripe Checkout's success/cancel redirect target) was hardcoded to `http://localhost` directly in `docker-compose.yml` instead of reading `${APP_BASE_URL}` from `.env` — fixed in both files, now `https://microverse.local`.
  - Also worth remembering: `docker compose up -d --force-recreate <service>` recreates the *container* from whatever image is already cached — it does **not** rebuild the image. Several recreates this session ran against a stale binary (hours old, missing in-progress fixes) with no indication anything was wrong beyond "no new log output." `docker compose build <service>` (or `up -d --build --force-recreate`) is required to actually pick up source changes.
